# Phase 1 Multi-Cloud GenAI Threat Model

Protect confidential enterprise knowledge across Azure, AWS and GCP through identity, application, workload, data and operational controls. A private network is one vault control; valid identities and authorized releases still require verification.

Design exercise. This report does not discover cloud resources or confirm vulnerabilities. Threats and scores require human review.

## Executive priorities

- T1 Stolen privileged session Current risk 20 (Critical); owner: IAM lead.
- T2 Cross-group document disclosure Current risk 20 (Critical); owner: Application owner.
- T3 Cross-cloud federation abuse Current risk 20 (Critical); owner: IAM lead.

## Assumptions and scope

- Illustrative design; no live resources were inspected. All controls are proposed and scores require review.
- Azure hosts an employee-facing containerized RAG assistant and managed model endpoint; AWS stores approved source documents; GCP handles ingestion and vector search.
- Enterprise identity provider authenticates employees. Separate workload identities query, ingest and deploy.
- Confidential data crosses cloud boundaries only after data-owner approval. Exact services, regions, retention and contracts remain open.
- No autonomous action tools; model training and provider physical controls are out of scope. Customer owns application authorization, IAM and resource configuration; provider responsibilities vary by selected service.

## Risk method

Likelihood and impact use ordinal 1-5 scales. Likelihood: rare, unlikely, plausible, likely, expected under the assumed weakness. Impact: negligible, limited, material team disruption, major business harm, broad confidential-data loss or privileged compromise. Score = likelihood x impact. Low 1-4; Moderate 5-9; High 10-16; Critical 17-25. Targets are conditional on control validation. Proposed controls do not lower current risk. Scores are judgments, not measured probabilities.

## Controls and validation


### T1 Stolen privileged session

Weakness: Standing privilege and weak change approval

Business impact: Stolen admin session plus standing privilege changes cross-cloud trust; broad data access. A4, TB1/3.

Owner: IAM lead

Prevent: Phishing-resistant MFA; time-bound admin; dual approval for trust edits

Detect: Alert on privilege activation and trust change followed by unusual reads

Respond: Disable identity; apply resource deny; remove trust; assess issued sessions

Recover: Restore reviewed IAM policies

Validation: Unapproved trust edit rejected; exercise session containment

### T2 Cross-group document disclosure

Weakness: Server trusts caller document IDs or ACL labels

Business impact: API trusts document IDs or caller ACL labels; employee retrieves another group's confidential chunks. A1-3, F3/5.

Owner: Application owner

Prevent: Server-side document authorization before retrieval, source fetch and citations; isolate caches

Detect: Alert on successful unauthorized canary retrieval and repeated denials

Respond: Disable affected retrieval route; invalidate caches

Recover: Repair ACL propagation and rebuild affected index

Validation: Two-user cross-group tests return zero unauthorized chunks, citations or cached answers

### T3 Cross-cloud federation abuse

Weakness: Wildcard subjects/audiences and excess resource permission

Business impact: Federation accepts broad subject/audience; compromised workload acquires unintended AWS/GCP permissions. A1/2/4, TB3/4.

Owner: IAM lead

Prevent: Exact issuer subject audience and environment bindings; separate query/ingestion identities

Detect: Unexpected role exchange or resource access

Respond: Remove trust and deny principal at resources

Recover: Rebuild scoped trust using reviewed IaC

Validation: Wrong issuer subject audience and environment all fail; valid identity has only required permissions

### T4 Retrieved prompt injection

Weakness: Untrusted text treated as instructions or excessive context sent

Business impact: Malicious retrieved text influences model; excessive context or unsafe rendering leaks data or misleads users. A2/3, TB2.

Owner: AI lead

Prevent: Separate instructions from content; minimize context; no model-controlled authorization; escape output

Detect: Track injection evaluation failures and anomalous citations

Respond: Quarantine content; disable unsafe feature

Recover: Restore approved prompt and trusted index

Validation: Adversarial documents cannot expand access or trigger actions; evaluate answer reliability separately

### T11 Destruction of data and recovery

Weakness: Same principal can delete production and every backup

Business impact: Attacker deletes source/index and backups using same authority; recovery fails. A1/2/6, TB6.

Owner: Platform lead

Prevent: Separate backup authority; retained versions; reviewed deletion policy

Detect: Backup retention changes and mass deletion

Respond: Freeze destructive identities; preserve surviving copies

Recover: Restore trusted source and ACLs into clean environment and reindex

Validation: Restore drill measures RTO 4h and RPO 24h targets; compromised production identity cannot delete all copies

### T5 Compromised production release

Weakness: Runner or dependency can publish unapproved privileged image

Business impact: Compromised dependency or runner publishes privileged image; runtime steals tokens and reads documents. A4/5, TB5.

Owner: DevSecOps lead

Prevent: Isolated builds; dependency checks; provenance/digest verification; independent release approval

Detect: Artifact drift and unusual runtime processes

Respond: Freeze releases; isolate workloads; deny identity

Recover: Rebuild clean artifact and redeploy reviewed version

Validation: Unapproved digest and unreviewed release rejected; record approval and provenance

### T6 Runtime credential theft

Weakness: SSRF or runtime compromise plus excessive workload privilege

Business impact: SSRF or runtime compromise reaches credentials; overbroad workload role enables secret/data reads. A1/4, TB2/3.

Owner: Platform lead

Prevent: SSRF input/egress checks; minimal identity grants; non-root workload; no unnecessary secrets

Detect: Unexpected metadata/secret/store access

Respond: Isolate runtime; deny identity; rotate exposed secrets

Recover: Rebuild clean workload

Validation: Bounded SSRF tests and permission checks prove non-required stores/secrets inaccessible

### T7 Confidential data exposure

Weakness: Public access permissive key grants or verbose prompt logs

Business impact: Public store, permissive key policy or verbose prompt logs expose confidential data. A1-4, TB3/6.

Owner: Data owner

Prevent: Block public access; scope decrypt grants; encrypt; redact logs

Detect: Exposure drift and unusual object/decrypt reads

Respond: Restrict resource; rotate exposed secrets; assess disclosure

Recover: Restore approved configuration

Validation: Verify anonymous access denied and test sensitive markers absent from logs

### T10 Request abuse or dependency outage

Weakness: No user quotas concurrency limits or timeouts

Business impact: User floods costly requests or dependency fails; no quotas/fallback produces outage and cost spike. A3, F2/5/6.

Owner: Application owner

Prevent: Per-user quotas; request/token limits; circuit breakers

Detect: Volume/spend twice baseline for 10 minutes; error/latency alert

Respond: Throttle requests; disable generation with safe unavailable response

Recover: Restore capacity and verify dependency health

Validation: Bounded load and dependency-failure test verifies caps and safe failures

### T8 Knowledge poisoning

Weakness: Unreviewed source writes or ACL metadata tampering

Business impact: Curator/connector can overwrite approved source and ACL metadata; poisoned knowledge corrupts answers. A1-3, F4.

Owner: Data engineering lead

Prevent: Read-only ingestion; approved source versions; provenance checks

Detect: Unexpected source version/hash or ACL drift

Respond: Stop ingestion and quarantine source

Recover: Restore trusted source/ACLs and reindex

Validation: Tampered source and ACL metadata quarantined; trusted reindex passes authorization tests

### T9 Audit suppression

Weakness: Production administrators can erase evidence

Business impact: Privileged actor disables audit or erases records; misuse cannot be attributed. A6, TB6.

Owner: SOC lead

Prevent: Independent restricted log destination and retention protections

Detect: Required log stream absent for 10 minutes or unapproved retention change

Respond: Preserve independent evidence; restrict destructive access

Recover: Restore collector and approved logging configuration

Validation: Safe log-disable event reaches SOC within target and production admin cannot erase archive

## Attack paths


### AP1 Stolen identity crosses clouds

Steal admin session > Edit federation trust > Assume broad AWS role > Read source documents > Exfiltrate

Threats: T1, T3, T7

Breakpoints: Time-bound privilege, independent trust approval, scoped object access and correlated data-read alerts.

### AP2 Private retrieval leaks documents

Authenticate as ordinary employee > Change document ID/filter > Retrieve unauthorized chunks > Model reveals confidential answer

Threats: T2, T4

Breakpoints: Server-side document ACLs before context assembly; per-user cache isolation and canary tests.

### AP3 Compromised release steals data

Compromise dependency or runner > Deploy malicious image > Steal runtime token > Assume cross-cloud role > Read data and suppress local logs

Threats: T5, T6, T3, T9

Breakpoints: Verified release digest, independent approval, narrow workload role and independent logs.

### AP4 Poisoned recovery

Modify approved source > Rebuild poisoned index > Overwrite recovery copy > Restore poisoned data

Threats: T8, T11

Breakpoints: Independent source approval, protected versions and tested clean reindex.

## Remediation and production gate

Before production: validate document authorization, federation claims and release integrity; test alert routing and clean restoration. Assign named owners. Review all remaining High/Critical risks with the security lead and business data owner. Record any acceptance, approver, compensating control and expiry. This generated report grants no approval.

## Incident response and recovery

Declare an incident and preserve evidence; isolate affected workloads and deny compromised principals in every cloud; assess source documents read or modified; fix root causes and rebuild clean artifacts; restore trusted source versions and ACLs, reindex and verify authorization before reopening. Removing trust alone may not invalidate issued sessions. Backups do not undo disclosure. Proposed recovery targets: RTO 4 hours and RPO 24 hours, pending business approval and restore testing.
